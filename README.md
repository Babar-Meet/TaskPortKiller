Professional Ports and Processes Management Tool for Windows.

A desktop application that displays listening ports and running processes, terminates unwanted processes, and force-deletes locked files or folders by leveraging Windows system utilities.

---

## Purpose

Windows provides no built-in GUI to quickly find which process is listening on a specific port or to force-delete a locked file without third-party tools. TaskPortKiller solves this by offering a single-window interface for:

- Viewing all listening ports and the processes that own them
- Viewing all running processes with resource usage
- Terminating processes by port number or process name (with safety guards)
- Force-deleting files or folders that are locked by other processes

It is intended for developers, system administrators, and power users who need fast, safe port and process management on Windows.

---

## Features

- **Listening Ports Table** — Displays protocol, local IP, port, PID, and process name for every active `LISTEN` socket.
- **Running Processes Table** — Shows PID, name, CPU %, memory (MB), thread count, status, username, and command line for each process.
- **Quick Kill by Port** — Enter one or more port numbers (space-separated) and kill all associated processes in bulk or one-by-one with confirmation.
- **Quick Kill by Process Name** — Enter one or more process name patterns and kill all matching processes.
- **Force Delete locked files/folders** — Automatically detects locking processes using Sysinternals `handle.exe` (optional) and `taskkill /F /T`, removes file attributes, and retries deletion with configurable retry count.
- **Configurable Auto-Refresh** — Both ports and processes tabs support automatic refresh with a user-adjustable interval (500 ms–60 s).
- **Column Sorting** — Click any column header to sort ascending/descending; numeric-aware and unit-aware (handles `%` and `MB` suffixes).
- **Search/Filter** — Filter ports or processes by any column value in real time.
- **Safety Guards** — Hard-coded protection against terminating critical system processes (`csrss.exe`, `wininit.exe`, `services.exe`, `lsass.exe`, `svchost.exe`), processes owned by `NT AUTHORITY\SYSTEM`, processes under protected directories (`C:\Windows\`, `C:\Program Files\`, etc.), and the application itself.
- **Show All toggle** — Optionally include system processes in the listing.
- **Dark Theme** — Modern dark blue/gray UI using `ttk.Style` with a custom color palette.
- **Multi-Desktop Awareness** — Uses `SetWindowDisplayAffinity` / `SetWindowLongPtrW` (Windows API) to keep the window on the current virtual desktop.
- **Resizable Window** — Minimum size 1000×500, default 1200×700.

### Request / Response Flow

1. User interaction → Tkinter event loop → bound callbacks on UI classes.
2. For data refresh: a daemon thread is spawned; it reads system data via `psutil` and schedules a UI update on the main thread via `parent.after(0, ...)`.
3. For kill/delete operations: a daemon thread executes the destructive action and schedules result display on the main thread.

### State Management

- UI state is stored in `tk.StringVar`, `tk.BooleanVar`, and plain instance attributes on the tab classes.
- The "Show All Processes" toggle is stored as a `BooleanVar` on `MainApplication` and read by both `PortsTab` and `ProcessesTab` on each refresh.
- The active tab is tracked by `MainApplication.current_tab`.

### Threading Model

- Every refresh and every destructive action runs in a **daemon thread** (`threading.Thread(daemon=True)`).
- UI mutations are marshalled back to the main thread via `parent.after(0, callback)`.
- During a kill/delete operation, all action buttons are disabled to prevent concurrent operations.

## How It Works

### Application Startup

1. `main()` checks that `psutil` is importable, then creates a `MainApplication` instance.
2. `MainApplication.__init__()` sets up the dark theme, builds the sidebar and tab container, creates the three tab instances, and shows the Quick Kill tab by default.
3. `set_window_desktop_affinity()` tries to pin the window to the current virtual desktop using Win32 API calls.
4. The tkinter main loop starts.

### Browsing Ports

1. User clicks "Ports" in the sidebar.
2. `PortsTab` starts its auto-refresh timer.
3. On each tick, a daemon thread calls `psutil.net_connections(kind="inet")` and filters for `LISTEN` state connections.
4. Each connection is enriched with the process name (via `psutil.Process(pid).name()`).
5. System processes are filtered out unless "Show All" is checked.
6. Results are matched against the search text and passed to `update_tree()` on the main thread.
7. The `Treeview` is cleared and repopulated; the current sort order is reapplied.

### Killing a Process

1. User selects a row and clicks "Kill Process".
2. `kill_port_process()` or `kill_process()` verifies the target is not the application itself and not a system process.
3. A confirmation `messagebox.askyesno()` is shown.
4. `proc.terminate()` is called.
5. On success, the table is refreshed.

### Quick Kill by Port

1. User enters port numbers (space-separated) in the Quick Kill tab.
2. `validate_ports()` parses and deduplicates them.
3. A daemon thread calls `kill_processes_by_ports()`, which:
   - Iterates `psutil.net_connections()` to find connections matching the ports.
   - Deduplicates by PID.
   - For each PID, validates safety rules and (optionally) asks for confirmation.
   - Calls `proc.terminate()`.
   - Collects results in a `{"success": [], "failed": [], "skipped": []}` dict.
4. Results are displayed in the results text area.

### Force Delete

1. User enters a file or folder path and clicks "Force Delete".
2. After confirmation, `release_and_delete()` runs in a daemon thread.
3. `get_handle_exe_path()` searches for `handle.exe`/`handle64.exe` in `tools/`, the script directory, and `PATH`.
4. If found, `get_locking_pids()` runs `handle.exe <path>` and parses PIDs from its output. It also checks every process's current working directory for overlap with the target path.
5. Each locking PID is killed via `taskkill /PID <pid> /F /T`.
6. The thread sleeps 1 second for handles to release.
7. `remove_attributes()` runs `attrib -r -s -h <path> /s /d` (falls back to `os.chmod`).
8. Deletion is attempted via `shutil.rmtree()` for directories or `os.remove()` for files.
9. If deletion fails with a lock-related error, the loop retries (up to 5 times by default).
10. Results are displayed or an error is raised.

## Safety Design

The application implements multiple safety layers before any destructive action:

1. **PID 0 and 140** are always skipped (System Idle Process / System).
2. **is_system_process()** rejects processes whose name is in `CRITICAL_PROCESS_NAMES` or `IGNORE_EXECUTABLES`, whose owner is `NT AUTHORITY\SYSTEM`, or whose executable path starts with any `IGNORE_PATHS` prefix.
3. **PID === own PID** is always rejected.
4. **User confirmation** is required for every kill operation (configurable per-operation in Quick Kill).
5. **Access Denied** and **NoSuchProcess** exceptions are caught and reported rather than causing crashes.

## Error Handling

- Every `psutil` call is wrapped in `try/except` blocks that catch `psutil.AccessDenied`, `psutil.NoSuchProcess`, and `psutil.ZombieProcess`.
- The force-delete logic has its own exception hierarchy: `DeletionError`, `HandleNotFoundError`, `MaxRetriesExceededError`.
- UI errors during refresh are caught and displayed via `show_error()` (a `messagebox.showerror()` wrapper).
- When the main thread needs to display an error from a background thread, it schedules `parent.after(0, show_error, ...)`.
- The `connect()`/`accept()` pattern is not used — this is a local-only application.
